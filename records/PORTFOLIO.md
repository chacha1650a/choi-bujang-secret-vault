- 사이트: https://aleph-omega.vercel.app/defense
- 배포 주소: https://choi-bujang-secret-vault-delta.vercel.app
- 제공 엔진: ALEPH SDP 엔진(이 저장소에 없음). 판정기·탐지 규칙·접속 앱·자료실·점검 코드는 학생이 만들었습니다.

### 진행 과정
1. 방어전 페이지에서 1단계 안내를 읽고, Vercel 클론 링크로 저장소 생성을 시도했다.
2. **문제**: Vercel의 "Preparing Git Repository" 단계에서 같은 오류("An unexpected error occurred")가 3회 연속 발생했다. GitHub에는 내용이 없는 빈 공개 저장소만 남고 Vercel 프로젝트는 에러 상태가 됐다.
3. **시행착오**

   - 실패할 때마다 빈 저장소와 에러 프로젝트가 남아 이름이 겹치므로, GitHub 저장소와 Vercel 프로젝트를 모두 지우고 다시 시도했다.
4. **해결**: Vercel 클론 대신 우회했다.
   - 시작 틀 저장소(ChoiTimo/aleph-defense-starter)의 "Use this template"으로 내 계정에 공개 저장소를 직접 만들었다.

5. 배포 후 Domains의 짧은 주소로 `/data.json`을 열어 공개 상태를 확인했다.

### 배운 점
- 사고는 대개 "처음부터 보안 없이 급하게 만든" 상태에서 시작된다. 공개 저장소와 공개 주소만으로도 자료가 그대로 노출된다.

- 외부 서비스(Vercel) 장애는 같은 방법을 반복하기보다 경로를 바꿔서(템플릿 + Import) 우회하는 게 빨랐다.

### 주의 사항

### 진행 과정
1. 안내 페이지의 이어받기·제작 1~3·제출 전 확인을 읽고 저장소를 클론해 현재 상태를 점검했다. 안내는 메모를 세 개라고 했지만 실제는 네 건이었다.
2. 제작 1: Supabase 프로젝트를 만들고(자동 공개 옵션 끔) schema.sql(테이블, RLS, anon/authenticated 권한 회수)을 실행. 메모 시드는 Git에 올라가지 않는 로컬 파일로 분리해 저장소에 메모 문장이 남지 않게 했다. 확인: 메모 4건, RLS 켜짐, anon/authenticated 권한 0, owner_id 있음, 외래키 없음.
3. 제작 2: api/notes.js 서버 함수(서버 전용 키는 Vercel 환경변수 SUPABASE_URL, SUPABASE_SECRET_KEY)와 화면 연결. 빌드가 public/data.json을 만들지 않게 바꾸고, step 검사 때문에 aleph.json이 안 만들어지는 문제를 고쳤다.
4. 제작 3: README에 확인 절차와 남은 약점을 기록.
5. **문제**: 배포 후 /api/notes가 500(NOTES_UNAVAILABLE). 원인은 자동 공개를 꺼서 서버 전용 키(service_role)에도 테이블 권한이 없던 것. has_table_privilege로 확인하고 grant select ... to service_role 한 줄로 해결, schema.sql에도 반영했다.

### 배운 점
- RLS를 켜는 것과 테이블 권한(grant)은 별개다. service_role은 RLS는 건너뛰지만 권한이 없으면 읽을 수 없다.
- 오류 응답에 자세한 내용을 넣지 않으면 원인 파악이 어렵다. 권한 조회 쿼리로 추측 대신 확인하고 고쳤다.
- 파일을 지워도 옛 커밋과 배포에는 노출 이력이 남는다. 해소됐다고 쓰지 않고 한계로 기록했다.
- 비밀 키는 채팅·코드에 넣지 않고 Vercel 환경변수에 직접 넣었다.

### 남은 약점
- /api/notes는 로그인 없이 누구나 호출 가능(3단계에서 해결).
- 1단계 때 공개된 옛 커밋·배포에 메모가 남아 있음.

## 4단계: 로그인해도 내 자료만 보이게 합니다

### 목표
- 로그인만 하면 남의 메모 id로 접근할 수 있는 문제(IDOR)를 막는다. 읽기·추가·수정·삭제 모두 서버가 검증한 사용자와 메모 소유자가 같을 때만 허용한다.
- 실제 사고 사례: 퍼스트 아메리칸 파이낸셜, 주소의 숫자만 바꾸면 남의 문서가 열린 사고.
- 막을 괴물: 심판 소유 메모 조회, 심판 소유 메모 수정, 시험 계정 B로 A의 메모 삭제.

### 결과물
- 커밋 9e17907(4단계 저장점). src/notes-api.mjs에서 id로 DB의 owner_id를 먼저 읽고 로그인 사용자와 다르면 403(본문 없음), 없으면 404. 주인 없는 옛 행도 기본 거부.
- 추가할 때는 항상 검증된 사용자 ID로 저장(본문의 owner_id는 무시), 소유자를 바꾸려는 수정은 403. 수정·삭제 쿼리에도 owner_id 조건을 한 번 더 붙임.
- DB: owner_id 연결, RLS 정책 4개(`(select auth.uid()) = owner_id`), 권한 최소화(supabase/rls-step4.sql). 계정 A·B를 만들고 A 메모 4건, B 메모 1건으로 정리.
- 테스트: 가짜 DB로 A/B 교차 접근 테스트 추가(test/notes-api.test.mjs).

### 진행 과정
1. 안내 프롬프트대로 현재 상태 점검 후, 테스트 계정 B를 가입했다. 이메일에 +별칭을 쓰면 같은 메일함으로 계정을 하나 더 만들 수 있다.
2. 제작 1~3을 순서대로 실행(SQL 한 묶음 ①②③). 이메일이 들어 있는 SQL은 .gitignore 처리한 로컬 파일로 분리.
3. **막힘**: 테스트 중 `PUT {}`가 400이 아니라 404로 나왔다. 존재·소유자 확인을 입력 검증보다 먼저 하기로 설계했기 때문이라 테스트 순서를 바꿨다.
4. Supabase가 `drop policy if exists`에 "Potential issue detected" 경고를 띄웠다. 내용을 확인하고 실행했다.
5. 직접 확인: A로 로그인하면 메모 4건, B로 로그인하면 B 메모 1건만 보임.

## 3차 필수 XDR 작전 6종: 최 부장 PC를 되찾습니다

### 목표
- Wazuh 경보(수업용 가상 경보)를 읽어 명확한 공격은 block, 애매한 시도는 alert, 정상 이벤트는 record로 나누고, 아주 명확한 경우에만 그 주소를 내 판정기에서 막는다.
- 과제: xdr-01 무차별 로그인(80) · xdr-02 웹 입력 조작(100) · xdr-03 알려진 취약점(120) · xdr-04 몰래 심은 프로그램(100) · xdr-05 권한 가로채기(100) · xdr-06 자료 빼돌리기(100).

### 결과물 (커밋 bb26c0a 공통 부품, ca3b6af~136347e 「보너스 xdr-01~06 저장점」)
- 모듈마다 `read-alerts.mjs`(시각·주소·계정·수준·설명만, 비밀값 가림) → `patterns.json`(MITRE ATT&CK·CVE 근거 한 줄씩) → `decide.mjs`(import 없이 패턴을 맨 위 상수로 옮겨 판단) → `respond.mjs`(block만 출발 주소 거부 규칙, 만료 60분·근거 경보 번호, `xdr/alerts.log`) → `result.json`.
- 확신도: 뚜렷한 공격 형태 + Wazuh 수준 10 이상이면 0.88~0.98(block), 공격 조각·한 번뿐인 시도는 0.5~0.8(alert), 나머지는 0.3 이하(record).
- 판정기의 기존 규칙·RULE_IDS는 그대로 두고, `src/xdr-gate.mjs`의 `withXdrGate`가 판정기 앞에서 거부 규칙만 확인(정책 사본 차이 없음, 12단계 기록 20/18/0/2 유지).
- 결과: 경보 160건 모두 기대대로(block 53 · alert 52 · record 55), 정상 이벤트 차단 0건, 거부 규칙 47개. 각 decide.mjs를 빈 폴더에 혼자 두고 불러와도 같은 답.
